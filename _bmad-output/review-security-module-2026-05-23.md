## Patch Findings — Critical / High

| #      | Title                                                                 | File:Line        | Source                                                                    | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------ | --------------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1     | TOTP has no replay protection                                         | `totp.ts:86`     | blind+edge                                                                | `verifyTOTPCode` with `drift=1` accepts any valid code for up to 90 s. No used-code record. A shoulder-surfed or intercepted code can be replayed within the window. NIST SP 800-63B §5.1.4.2 requires OTPs not be accepted more than once per validity period. Fix: add `lastUsedCounter` to `TOTPConfig`; reject any `T` ≤ last accepted.                                                                                                                                      |
| P2     | Vault file import overwrites IDB before password verification         | `auth.ts:149`    | blind+edge                                                                | `open-vault-btn` handler writes `salt`, `verify`, `vault` from a user-supplied JSON file directly into `nexus_vault_v2` IDB after only a version and type check — no password verification. The current session's live vault is silently replaced. A socially-engineered malicious file clobbers the user's real data with no recovery path. Fix: verify password against the file's verify token before overwriting IDB; show a "this will replace your current vault" warning. |
| P3     | `changePassword` does not re-encrypt IDB-backed stores                | `vault.ts:189`   | blind+edge                                                                | `changePassword` re-encrypts the vault blob (`STORES`) under the new key but the per-record IDB stores (`documents`, `conversations`, audit log `__audit_log__`, TOTP config `__mfa_totp__`, passkeys `__mfa_passkeys__`, AI secrets `__ai_secrets__`) in `nexus_data_v1` remain encrypted under the old derived key and become permanently unreadable after the change. Fix: after re-encrypting the vault blob, also iterate and re-encrypt every record in `IDB_STORES`.      |
| P4     | `sanitizeDataUrl` allows arbitrary `data:` URIs                       | `sanitize.ts:39` | blind                                                                     | Any string starting with `data:` (case-insensitive) is returned unchanged. This permits `data:text/html,<script>alert(1)</script>`, `data:application/javascript,…` etc. in `href`/`src` attributes. Fix: whitelist only `data:image/` MIME prefixes (plus `data:application/octet-stream` if needed for downloads); reject all others.                                                                                                                                          |
| P5     | `importEncryptedBackup` forced KDF downgrade via any decryption error | `vault.ts:229`   | blind                                                                     | The 310k-iteration fallback triggers on **any** exception from the 600k decrypt, not just wrong-KDF conditions. A crafted backup that reliably fails AES-GCM auth forces the weaker path. Fix: catch the specific error type (e.g. `OperationError` from WebCrypto), not a bare `catch {}`; only fall back on that specific case.                                                                                                                                                |
| P6     | `importEncryptedBackup` performs no schema validation after decrypt   | `vault.ts:241`   | edge                                                                      | Decrypted payload is cast directly to `Record<string, unknown[]>` and saved. Unlike `importJSON`, `validateImportPayload` is never called. A malicious or corrupted backup can inject arbitrary structures into every `STORES` key. Fix: call `validateImportPayload` on the decrypted vault before `saveVault`.                                                                                                                                                                 |
| P7     | TOTP MFA step has no rate limiting or lockout                         | `auth.ts:397`    | edge                                                                      | The password form has exponential backoff + localStorage lockout. The TOTP form (`_showTOTPStep`) has no fail counter, no delay, and no lockout. All 1,000,000 codes can be enumerated in a script after the password is known. Fix: add a TOTP attempt counter (sessionStorage, cleared on success) with the same exponential backoff as the password form.                                                                                                                     |
| P8     | `_checkMFAStep` silently bypasses MFA when IDB hook is not injected   | `auth.ts:315`    | edge                                                                      | `_idbLoadStore` defaults to `null`. If `setAuthIDBHooks` has not been called by the time `_checkMFAStep` runs (hook injection race), the `if (_idbLoadStore)` block is skipped, `totpEnabled` stays `false`, and `onSuccess(key)` fires unconditionally — MFA is bypassed with no error. Fix: throw (or bail to an error screen) rather than silently proceeding if `_idbLoadStore` is null when TOTP is expected to be checked.                                                 |
| ~~P9~~ | ~~Audit log `_appendToLog` race condition breaks hash chain~~         | `audit.ts:175`   | ✅ **Fixed with D1** — serial `_writeQueue` eliminates concurrent writes. |
| P10    | `webauthn.ts` local `_u8ToBase64` violates Security Rule #6           | `webauthn.ts:23` | blind+auditor                                                             | Implements char-by-char `str += String.fromCharCode(u8[i]!)` then `btoa(str)` — functionally identical to the banned `btoa(String.fromCharCode(...array))` pattern. Comment on line 22 acknowledges the risk but does not resolve it. For large `rawId` or `encPassword` blobs this is a stack-overflow hazard. Fix: replace both `_u8ToBase64` and `_base64ToU8` in `webauthn.ts` with `u8ToBase64` / `base64ToU8` imported from `./crypto.js`.                                 |
| P11    | `loadMFAStatus` exposes raw TOTP secret to every caller               | `mfa.ts:83`      | blind+edge+auditor                                                        | Returns `totpSecret: cfg?.secret \|\| ''` — the base32 seed — to all callers. Only `totpEnabled` (boolean) is needed by the auth flow. The secret sits in module-level variables in the view layer. Fix: remove `totpSecret` from `MFAStatus`; add a separate `getTOTPSecret(): Promise<string>` for the explicit QR-code display path only.                                                                                                                                     |

## Dismissed (4)

| #   | Finding                                                            | Reason                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | `_rawPolicy` is a no-op pass-through applied to every `innerHTML`  | By design — the security model requires all user data to go through `escH()` before template strings. `_rawPolicy` satisfies the Trusted Types API contract for pre-built template HTML. |
| R2  | `_ttPolicy` naming is misleading as a TT `createHTML` policy       | Design-intentional; `_ttPolicy` is used explicitly for user-text escaping, not as the global `innerHTML` interceptor.                                                                    |
| R3  | No sanitization fallback in browsers without Trusted Types support | Fallback unnecessary — Trusted Types enforcement only applies in browsers that support and enforce it.                                                                                   |
| R4  | `CryptoKey` remains in memory after `clearSessionKey`              | WebCrypto spec does not provide a zeroing API. Callers must nullify references; no code fix possible.                                                                                    |
